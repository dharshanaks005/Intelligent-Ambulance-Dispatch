# Project: Intelligent Ambulance Dispatch and Routing System

## 1. Project Overview

Build a complete, functional, simulation-based web application called **“Intelligent Ambulance Dispatch and Routing System”** using Python, Streamlit, NetworkX, Folium, and OpenStreetMap.

The goal is to simulate how an intelligent emergency response system dispatches the most suitable ambulance to a patient's location and dynamically reroutes it when road incidents or traffic disruptions occur.

This project is intended for academic demonstration and simulation purposes. It must demonstrate intelligent ambulance selection, road-network-based route planning, estimated travel times, incident detection, dynamic rerouting, and a clear visualization of the entire process.

**Important: Use Streamlit as the primary user interface. Do not replace it with React, Flutter, or another frontend framework. Do not introduce FastAPI or a separate backend unless it becomes genuinely necessary.**

Build the application as a working project, not merely a prototype with static screens.

## 2. Required Technology Stack

Use the following technologies:

- **Python:** Core application logic and simulation.
- **Streamlit:** Web interface and dashboard.
- **Folium:** Interactive map visualization.
- **streamlit-folium:** Display and interact with Folium maps in Streamlit.
- **NetworkX:** Road graph representation and shortest-path calculations.
- **OSMnx, if appropriate:** Optional support for downloading and processing real road networks from OpenStreetMap. If the existing implementation uses a custom Overpass API graph builder, preserve and improve it instead of unnecessarily rewriting it.
- **Geopy:** Geographic distance calculations where appropriate.
- **Requests:** Fetch road network data from OpenStreetMap's Overpass API.
- **Python standard libraries:** Caching, data processing, validation, and simulation state management.

Keep the application compatible with Replit's Python environment.

## 4. Intelligent Ambulance Dispatch

Create a dispatch mechanism that selects an ambulance based on its suitability for responding to the emergency.

Initially simulate at least three ambulances in a configurable geographic area around Thrissur, Kerala, India.

Each ambulance should have:

- A unique ambulance ID.
- A current latitude and longitude.
- An availability status.
- An optional assigned-patient status.
- A simulated operational state, such as available, dispatched, or responding.

Allow the user to enter or adjust the patient's latitude and longitude.

When the user clicks **“Find Best Ambulance”** or **“Dispatch Ambulance”**, the system should:

1. Identify available ambulances.
2. Calculate a feasible road route from each eligible ambulance to the patient.
3. Estimate the travel time for each route.
4. Compare the candidates.
5. Select the ambulance with the lowest estimated response time among feasible candidates.
6. Display the selected ambulance, route distance, estimated response time, and other candidates for comparison.

Do not select an ambulance solely using straight-line geographic distance if road-network routes are available.

If the road network or route calculation is unavailable, show a clear error or explicitly labelled fallback result rather than silently pretending that a road route was calculated.

Make dispatch scoring modular so that future versions can incorporate emergency severity, ambulance capacity, equipment, hospital availability, or other factors.

For the initial simulation, document the selection criteria and use only the factors that are actually implemented.

## 5. Road Network and Route Calculation

Use real road-network data from OpenStreetMap where available.

The system should:

1. Download the relevant road network using the existing graph-building logic or an appropriate OpenStreetMap library.
2. Represent roads as a NetworkX graph.
3. Associate road edges with distance and estimated travel-time weights.
4. Find the nearest graph nodes to the ambulance and patient coordinates.
5. Compute the fastest feasible route using Dijkstra's algorithm or another appropriate shortest-path algorithm.
6. Convert the resulting graph path into geographic coordinates for map rendering.

Use edge travel-time weights rather than relying only on the number of graph edges.

If edge speeds are unavailable, use a configurable, clearly documented speed assumption. Treat resulting times as estimates, not live traffic predictions.

Cache downloaded road networks where appropriate to avoid repeatedly querying the Overpass API whenever Streamlit reruns.

Handle API timeouts, rate limits, invalid coordinates, missing routes, and empty graphs gracefully.

If live road-network data cannot be fetched, explain the problem to the user. A deterministic offline demonstration mode may be provided, but clearly label it as simulated data.

## 6. Dynamic Ambulance Rerouting

This is one of the most important features of the project.

Simulate road incidents that may affect the ambulance's planned route. Examples include:

- A road obstruction.
- A traffic slowdown.
- An accident-related delay.
- A temporary road closure.

Provide simulation controls for:

- Incident severity.
- Incident confidence.
- Confidence threshold.
- Incident persistence.
- Ambulance progress along the planned route.
- Incident activation or deactivation.

Use the existing simulation logic as the starting point if it already contains these parameters.

### Required incident behavior

1. Calculate the original shortest or fastest route.
2. Display the original route on the map.
3. Simulate an incident affecting an edge on that route.
4. Evaluate whether the incident should trigger rerouting using the configured severity, confidence, threshold, persistence, and simulation progress.
5. If the incident is not sufficiently confirmed or persistent, retain the original route.
6. If the incident becomes active, modify the affected road edge's travel time or mark the edge as blocked.
7. Recalculate a feasible route from the ambulance's current simulated position to the patient's location.
8. Display the alternative route and calculate its estimated remaining travel time.
9. Compare the original and adjusted travel times.
10. Explain why rerouting occurred or why the original route was retained.

Do not implement rerouting by simply reversing a route or drawing an arbitrary line to the destination. The alternative must be calculated using the road graph.

### Important technical requirements

- Preserve the original graph and create a modified copy for incident simulation.
- Do not permanently modify the cached base graph.
- Do not repeatedly multiply already modified edge weights on every rerun. Always calculate the modified weight from the original base weight.
- Ensure a blocked edge cannot be selected as a valid route.
- Check that a route exists before calculating its travel time.
- Never return infinity or NaN as JSON-like data or display these as ordinary travel-time values.
- Avoid restarting the entire simulation unexpectedly when a user changes a slider.
- Make the incident state and ambulance progress consistent across Streamlit reruns.

If the alternative route is impossible, display a clear message and preserve the last valid route or report that no feasible route exists.

## 10. Intelligent Features and Metrics

The project should demonstrate actual algorithmic behavior, not just map visualization.

Implement and document:

- Road-network-based ambulance selection.
- Shortest or fastest path calculation.
- Incident-aware route recalculation.
- Confidence-based incident activation.
- Persistence-based incident confirmation.
- Route comparison before and after an incident.
- Estimated response-time improvement or delay.
- Ambulance progress along the route.
- Feasibility checks for alternative paths.

Calculate:

Time difference = adjusted estimated travel time − original estimated travel time.

A positive value indicates additional time; a negative value indicates a time saving.

If the adjusted route is calculated from the ambulance's current position, compare it against the original route's remaining travel time from that same position, not against the original full trip duration. Keep elapsed time and remaining time separate.

Do not claim that the application predicts real traffic or detects real accidents unless actual data sources are integrated. This is a simulation-only project, and its assumptions should be stated clearly.

## 11. Validation and Error Handling

Handle the following cases:

- Invalid latitude or longitude.
- Missing patient coordinates.
- No available ambulances.
- Road-network download failure.
- Overpass API timeout.
- Missing graph nodes.
- No path between ambulance and patient.
- Incident placed on an invalid edge.
- Alternative route unavailable.
- Invalid confidence or severity values.
- Missing or invalid simulation state.

Display friendly error messages in Streamlit.

Do not crash the application when an external API is temporarily unavailable.

Use caching carefully and do not cache mutable simulation state in a way that allows one simulation run to corrupt another.
